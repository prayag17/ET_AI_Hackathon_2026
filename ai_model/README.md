# AI Model

This folder contains the AQI forecasting pipeline used by the project. It turns city-level air quality data into a grid-level feature store, builds simple baseline forecasts, trains LightGBM models for 24, 48, and 72 hour horizons, and prints a scorecard comparing the model against baselines.

## What the model does

The model predicts future AQI for each 1 km grid cell in Ahmedabad. It uses historical AQI, pollutant estimates, weather context, traffic patterns, and engineered time features to forecast three horizons:

- 24 hours ahead
- 48 hours ahead
- 72 hours ahead

The training script fits one model per horizon and saves both the trained models and the prediction outputs for downstream use.

## Pipeline Summary

```text
city_hour.csv + sensor_locations.csv + weather_history.csv + grid geojson
	-> build_feature_store.py
	-> feature_store.csv
	-> baseline.py
	-> with_baselines.csv
	-> features_ready.csv (required, generated by an upstream step not included here)
	-> train.py
	-> model_24h.pkl, model_48h.pkl, model_72h.pkl
	-> model_predictions.csv
	-> scorecard.py
```

## Model Specifications

### Prediction target

- Target variable: AQI
- Output granularity: one forecast per grid cell
- Forecast horizons: 24h, 48h, 72h
- Model type: LightGBM regression

### Input features

The model expects the following columns in `data/features_ready.csv`
(see `FEATURE_COLUMNS` in `train.py`):

- `wind_speed`
- `temp`
- `humidity`
- `traffic_index`
- `hour`
- `dow`
- `hour_sin`
- `hour_cos`
- `dow_sin`
- `dow_cos`
- `is_public_holiday`
- `is_weekend`
- `month`
- `is_crop_burning_season`
- `is_diwali_window`
- `aqi_lag_3h`
- `aqi_lag_6h`
- `aqi_lag_24h`
- `aqi_roll_mean_24h`
- `aqi_roll_std_24h`
- `aqi_trend_6h`

### Training method

- Split strategy: time-based split, not random split
- Training split: first 80% of rows by timestamp
- Test split: last 20% of rows by timestamp
- Tuning: tries four LightGBM configurations per horizon and keeps the one with the lowest RMSE

### Baselines

The scorecard compares the model against two simple baselines:

- Persistence baseline: reuse the AQI from `h` hours ago
- Seasonal baseline: reuse the AQI from 168 hours ago

## Data Inputs

The pipeline relies on these files:

- `ai_model/data/city_hour.csv` - city-level hourly AQI history
- `ai_model/data/sensor_locations.csv` - sensor coordinates and IDs
- `ai_model/data/features/weather_history.csv` - weather history used to build seasonal weather features
- `backend/static/ahmedabad_1km_grid.geojson` - 1 km grid geometry and centroids

The training step also requires `ai_model/data/features_ready.csv`. That file is not generated by the scripts in this folder, so it must be produced by an upstream feature-engineering step before training.

## How to Run

Run commands from the repository root unless noted otherwise.

### 1. Prepare the grid

If the Ahmedabad 1 km GeoJSON grid is missing, generate it first from the backend utility that creates `backend/static/ahmedabad_1km_grid.geojson`.

### 2. Build the feature store

```powershell
cd D:\Github\ET_AI_Hackathon_2026\ai_model
python build_feature_store.py
```

This writes `data/feature_store.csv`.

### 3. Build baselines

```powershell
python baseline.py
```

This writes `data/with_baselines.csv`.

### 4. Provide `features_ready.csv`

Before training, make sure `data/features_ready.csv` exists and contains the exact feature columns listed above.

### 5. Train the model

```powershell
python train.py
```

This trains the three LightGBM models, saves the `.pkl` files, and writes `data/model_predictions.csv` and `reports/tuning_log.csv`.

### 6. Evaluate the scorecard

```powershell
python scorecard.py
```

This prints RMSE, MAE, skill score, and feature importance summaries.

### 7. Optional: wind ventilation signal (issue #40)

```powershell
python wind_signal.py
```

`wind_signal.py` derives a wind-based dispersion signal from existing columns
(`ventilation_index` = diurnal/temperature mixing-height proxy × wind speed,
plus a `poor_ventilation` flag) and A/B-trains the full `train.py` config grid
with and without it, printing an RMSE comparison per horizon.

**Recorded result (2026-07-14):** all deltas were within noise (<0.1% of a
~15.5 baseline RMSE), so the signal is **not** part of `train.py`'s
`FEATURE_COLUMNS` — the issue allows dropping it when it doesn't help. The
module stays available for re-testing if richer weather data (real wind
direction, observed mixing height) is ever added. A directional
spread-to-neighbours feature isn't computable from `features_ready.csv` at
all: its synthetic `cell_000`-style ids carry no coordinates.

## Notes

- `train.py` assumes the input rows are already aligned per grid cell and timestamp.
- The training code uses a time-based split to avoid leaking future data into training.
- If model quality is weak, the next place to inspect is the feature-engineering step that produces `features_ready.csv`.
